## Root cause found in staging

The module placed the DTB at `image_phys + PAGE_ALIGN(file_size)` = `image_phys
+ 0x1a0c000`. The Image file is 27,308,544 bytes, but its header `image_size`
is `0x1bef000` and `__bss_stop - _text = 0x1be9324`. `__primary_switched()`
clears BSS before `start_kernel`, so the DTB was zeroed before
`setup_machine_fdt()` could read it. `fixmap_remap_fdt()` then failed its magic
check and returned NULL, which is exactly the observed `0x5282` branch.

Fix applied to `work/r1-kexec/modules/r1_main.c`: read `image_size` from Image
byte 16, compute `image_span = PAGE_ALIGN(max(image_size, file_size))`, and use
that for both the CMA allocation and the DTB offset. With this fix the DTB
starts at `image_phys + 0x1bf0000`, past `__bss_stop`.

After this fix the crumb reads became inconsistent (`0`, `0x07501120`,
`0x0a8d8800`), and no boot to userspace was confirmed. The last value is not
any marker written by the instrumented kernel, so the crumb is being reused or
cleared later in boot. The instrumented kernel had
`cpu_uninstall_idmap()` commented out for diagnostics; that change is not a
real kernel change and must be reverted. The final clean build removed the
diagnostic vectors/markers again and kept only the original physical
`R1_MARKP` crumbs plus `r1_mark()` calls after `setup_arch`.

## CMA pools

`0x3d800000` (32 MiB, previously reported free) returned `-EBUSY` from

and the default CMA also returned `-EBUSY`. `0x2ac00000` (codec_mm) worked

## Answers to the open questions

- **Last marker / first missing:** historically `0x5260` / `0x5261`. On
  hardware this round, `0x5261` was produced once the idmap crumb block was
  fixed, so the original "hang at `msr sctlr_el1`" reading is refuted.
- **EL, VHE, `HCR_EL2.E2H`:** expected EL2 with VHE (`el2_setup` writes
  `HCR_RW|HCR_E2H|HCR_TGE`); not read on hardware.
- **Register values at fault:** not captured. `ESR`, `FAR`, `ELR`, `SPSR`,
  `SCTLR`, `TCR`, `VBAR` values remain unobserved; no numbers are invented.
- **Fault class:** not a translation fault from the markers. The observed stop
  was a software infinite loop on invalid DTB, later addressed by the staging
  fix. A remaining cause after that fix is not identified.
- **Linear map before `start_kernel`:** no. `0xffffff8007501000` is not mapped
  there; it is not even the linear-map address.
- **`paging_init` / `start_kernel` / Android:** with diagnostics, `start_kernel`
  and `setup_arch` were reached. After `setup_arch` no marker was seen in the
  early runs; after the staging fix, crumb reads were inconclusive. Android did
  not boot in any run.
- **Stock decrypted vs custom:** both watchdog-reset. The stock Image has no
  markers, so it cannot localize the stop.
- **What changed:** diagnostic writes were removed again; the real change is the
  module's use of the Image header `image_size` so the DTB is not zeroed with
  BSS. This does not alter kernel boot logic.

## Verdict

- Marker-induced fault: **REFUTED** on hardware (`0x5261` and later markers were
  produced once crumbs were mapped correctly).
- DTB zeroed by BSS clearing: **FOUND and FIXED** in the module; the `0x5282`
  branch is explained by it.
- Kernel reaching `start_kernel`: **PROVEN** with diagnostics.
- Kernel reaching userspace: **NOT ACHIEVED**. No `r1probe=DEADBEEF`, no new
  banner, no `sys.boot_completed` from the new kernel.
- Exception registers: **NOT CAPTURED**.

### Offline CMA audit - hypothesis REFUTED, no DTB change made

`dtc -I dtb -O dts work/r1-kexec/aquaman-r1.dtb` shows:

- `linux,codec_mm_cma`: `shared-dma-pool`, `reusable`, `size = 0xd000000`
  (208 MiB), `alignment = 0x400000`, `linux,contiguous-region`. It has NO
  `reg` and NO `alloc-ranges`, so its base is chosen at boot by
  `__memblock_alloc_base()`, not fixed at `0x2ac00000` by the DTB.
- Other pools: `di_cma` 32 MiB, `ion-dev` 76 MiB, `vdin1_cma` 16 MiB,
  `secmon` 4 MiB with `alloc-ranges` at `0x5000000`, `meson-fb` 8 MiB with
  `alloc-ranges` at `0x3f800000`, ramoops `reg` at `0x7400000..0x7600000`.
  None declares a fixed region covering the image at `0x2ac80000`.
- The live FDT pulled read-only from `/sys/firmware/fdt` (61,440 bytes,
  sha256 `a4ff2fb7ef77d7a91f59d78b8c2085a94b6f461d20fed45726d955168c557ba7`)
  has the same node sizes; live dmesg reports the old kernel's pool at
  `0x2ac00000, size 208 MiB`. The base is a boot-time placement, not a DT
  constant.

`arch/arm64/mm/init.c:284` reserves the running kernel with
`memblock_reserve(__pa_symbol(_text), _end - _text)` BEFORE
`early_init_fdt_scan_reserved_mem()` (line 295) and
`dma_contiguous_reserve()` (line 303). `head.S:471-473` sets
`kimage_voffset = kimage_vaddr - x0`; the module adds
`text_off & (2M-1) = 0x80000` so `(0x2ac80000 - 0x1080000) & 0x1fffff = 0`,
i.e. KASLR offset 0 and a correct self-reservation of
`0x2ac80000..0x2c86f000` (`_end - _text = image_size = 0x1bef000`).
Memblock cannot place CMA on top of that reserved range.

`aml_cma_alloc_range()` was also checked: `end` is exclusive in every loop
(`while (pfn < end)`), the module passes `start_pfn + count`, and the request
is about `0x21f3000` bytes, well inside the 208 MiB pool. No PFN
off-by-one or pool-overflow was found.

REFUTED statically. `patch_dtb.sh` and the DTB were left unchanged; changing

### Fire 11 fault analysis
The complete console record was still available locally as
`/tmp/opencode/r1-console-fire11.txt` (32756 B). It contains exactly one
fault line, `[9.313293@2] Unhandled fault: synchronous external abort
(0x82000010) at 0x0000000000049104`, then
`[9.316374@2] Kernel panic - not syncing: Attempted to kill init!
exitcode=0x00000007` and a trace ending in `complete_and_exit` ->
`do_group_exit` -> `get_signal` -> `do_signal` -> `do_notify_resume` ->
`work_pending`. No PC/LR/ESR register block is in the record: this kernel
only prints `show_regs()` when `show_unhandled_signals` is set, and it was
not. `dmesg-ramoops-0` was not present on the device after recovery.
ESR `0x82000010` decodes with `arch/arm64/include/asm/esr.h` as EC `0x20`
(`ESR_ELx_EC_IABT_LOW`), FSC `0x10` (`ESR_ELx_FSC_EXTABT`), with EA and
S1PTW clear: an instruction abort from EL0 where translation succeeded and
the fetched physical location returned an external abort. `fault_info[16]`
in `arch/arm64/mm/fault.c` sends it to `do_bad` with SIGBUS, which matches
`exitcode=0x00000007`.
The real `/init` was extracted read-only from `mmcblk0p18` with
`dd if=/dev/block/system bs=1048576 count=64` piped to a host file and
`debugfs -R 'cat /init'`: ELF32 ARM, 1501480 B, entry `0x9da5`, one RX LOAD
at `0x8000` with file size `0x1555a8`, `.text` `0x8160`-`0x132494`, sha256
`3f2ad2529d92e3b6da16bc786f3cf78dea527af5f202c32d331a259016f8d450`.
`0x49104` is inside that `.text` (file offset `0x41104`) and decodes in
Thumb as `push {r4, r5, r6, r7, lr}`, a normal function prologue. It is not
a kernel address in `build-aq/System.map`, and the earlier 32-bit `aq_init`
(`0x16a40`-`0x3828c`) is a different binary. So the fault is an instruction
fetch from a valid address in Android init's own text, not a bad ELF entry
or a kernel symbol.
### Hypotheses ordered
1. Userspace page-table or memory-attribute defect for the 32-bit compat
   process: BEST FIT. Translation completed and the fetch itself raised an
   external abort, which points at a wrong PTE target/attributes rather
   than a missing mapping.
2. Direct ext4 mount without dm-verity while cmdline says `root=/dev/dm-0`:
   WEAKER. It could corrupt file data, but a corrupt ELF would more likely
   give a translation/permission fault or illegal instruction, and init had
   already executed a long stretch of text before the fault.
3. Manual chroot without `/dev`, `/proc`, `/sys`: REFUTED as the direct
   cause of this fault. An MMIO access from init would be a data abort
   (EC `0x24`), not an instruction abort inside its own `.text`.
4. DTB/initrd staging corruption: WEAKER. The initrd wrapper and the ELF
   ran far enough to mount ext4 and reach a late init function.
5. DMA/GIC state inherited from the previous boot: INCONCLUSIVE but no
   supporting evidence in the console log.
