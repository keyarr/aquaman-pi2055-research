## 2. Critical discovery: the marker spray refutation is invalid

Offline analysis of 2026-11-19 (section 1.8) found that
`marker_spray.S` encoded the address as `base + 0x8e`:

```
movz x11, #0x008e
movk x11, #0x0108, lsl #16    // 0x0108008e
```

The real offset of `linux_banner` in the Image is `0xd4008e` (address `0x1dc008e`
for the base `0x1080000`). The round65 spray test wrote to `base + 0x8e`
at the six bases - it never touched the banner. Therefore:

- **INVALIDATED** the conclusion "the executed copy does not come from any of the buffers
  written" from round65 item 3.
- **VALID** only the refutation of `0x1080000` (marker.S, correct offset):
  `/proc/version` returned `4.9.113`.
- The location of the executed kernel copy **remains open**. Chain A
  is not dead; what was missing was the right experiment, not a barrier.

This is the most important point of the resumption: the previous round ended early
because of an offset error, not for lack of a path.

## 6. Security corrections from the SMC analysis (completed in this session)

- **Cmds `0x10/0x11/0x12/0x20` of `0x820000ff` ARE EFUSE PROGRAMMING**
  (`.src/u-boot-khadas/arch/arm/include/asm/arch-gxl/bl31_apis.h:110-115`,
  `common/cmd_efuse.c:189,211,233,255`). Irreversible, risk of brick.
  Previous reports (`round59/03`, `new-smc-repeatability`) incorrectly
  classified them as "status/OK". **NEVER send.** The cheapest and most
  informative is `0x80` (`AML_D_P_UPGRADE_CHECK`, non-mutating) or
  `0x40` itself (`AML_D_P_IMG_DECRYPT`), one cmd per session.
- `0x37e19310` is `flush_dcache_range`, not "global cache/TLB maintenance".
  The NOP at `0x37e19ee8` removes only this clean - **already tested with cmd
  `0x100` and REFUTED** (gadget froze, 2nd power cycle;
  `resume-2026-11-19-experiments.md:36`). Contradicts E14/H5. Do not reuse
  it as a "fix": it is diagnostics, and if it goes down, repeat in another session without NOP.
- Useful differential: `magisk_patched-30700_X0fyo.img` keeps the 512 B
  signature of stock at `0xE00`, but changes `ramdisk_size` at `+0xC`, the 20 B
  field at `0x240` and the ramdisk payload at `0x959800+`. Experiment N3 measures whether
  the SMC's `x0` depends on the modified content - but the gate is NOT a demonstrated
  block and bypass is unnecessary if the intervention is post-decrypt.
- Analysis verdict: N3 does not close root. The link remains the executed
  copy with the corrected offset (Chain A / E2b).

## 7. UHID analysis (completed in this session) - real disclosure bug

- **Correction:** the RW `open` of `/dev/uhid` by the `u:r:shell:s0` domain WAS
  already proven by hardware on 2026-10-01
  (`reports/dev-read-surface-census-2026-10-01.md:30,153`: `fd=3 poll=0
  read=EAGAIN`). It is no longer a SELinux doubt. Today's `ls -l` only reconfirms
  the DAC (group 3011).
- **Concrete bug in `.src/linux-amlogic/drivers/hid/hid-core.c:1464-1505`:**
  `hid_report_raw_event` clamps `rsize` to `HID_MAX_BUFFER_SIZE` (4096) only
  for the `memset`, but passes `cdata` to `hid_input_field` (`:1268-1318`) without
  a size. `hid_field_extract`/`__extract` (`:1086-1116`) reads `report[idx]` without
  a bounds check. The uid=2000-controlled descriptor allows
  `report_size<=128`, `report_count<=12288` -> `report->size` ~1.57M bits; the
  real buffer `UHID_DATA_MAX=4096`. `idx` exceeds 4095.
- **Why it can leak and not just panic:** `data` points into the middle of
  `struct uhid_device` (`uhid.c:41`, a single `kzalloc`); right after
  `input_buf.u.input.data[4095]` are the fields of the object itself, including
  `outq[32]` with kernel pointers filled by `UHID_START` during the
  probe (`uhid.c:110-134`, `:76-90`). Modest offsets read bytes from those
  pointers without crossing a page; `hidinput_hid_event` passes `value` on to
  `input_event`, observable in `/dev/input/eventN` (shell in group 1004).
- **Capability:** deterministic DISCLOSURE of kernel heap VA - exactly
  the anchor that Chain C (GhostLock, 0 bytes of VA) could not get. **No**
  write to a chosen address. Alone it does not deliver uid=0; it needs a separate
  write primitive. Classified as "potential disclosure", not as
  escalation.
- Secondary bug (not exploitable): in the numbered case, `memset` writes one zero
  byte to `data[4096]`, inside the `union uhid_event` itself.
- Risk: large offsets (~196 KB) cross an unmapped page and give an almost
  certain panic. **Do not run the exploit without an explicit decision and authorization.**
  Phase 1 (open/close + /dev/input) is cheap and safe for when the device
  returns.

## 8. USB analysis (completed in this session) - cache corrections

- **The N1 discriminator is dcache, NOT icache.** `flush_cpu_cache()` is an empty
  macro (`platform.h:65`); there is no flush in the bulk path. `SCTLR_EL1 I=0`
  (icache OFF, `bl33-control-primitive-round37.md:122`) and dcache ON.
  The `icache flush` idx 60 is harmless but irrelevant. The cause of P3/P9 is
  stale dcache, not icache.
- `0x06 WRITE_AUX` does NOT reach MMIO up to 0xFFFFFFFF: sign-extension in
  `(wValue<<16)+wIndex` limits the range, and `dwc_otg_ep_req_start()`
  reprograms the DMA address on every transfer. No gain. `0x07 READ_AUX`
  returns zero (stub). `0x12 RD_LARGE_MEM` is dead. `0x04/0x05` only DoS.
- `0x30/0x34` -> `optimus_working()` -> `run_command()`: the device does NOT have
  a filter; the "denylist" is client-side only (`tools/optimus.py:76`). Any
  U-Boot command is reachable.
- **No new read primitive** outside `0x02` and `0x33`. `md`/`sha1sum`
  print to an invisible console and return only `success`. Fastboot BL33 has no
  `oem` that returns RAM.
- 0x11 WR_LARGE_MEM is a write accelerator (a stub of any size in one
  transfer), not a path to uid=0. Risk: declaring `len` larger than the
  bytes sent wedges `do_bulk_complete()` by re-arming DMA with no data (a wedge
  with no abort in the code). Never do this.
- Verdict: naive N1 with dcache flush; if `false->success` in both phases,
  N1 is negative (USB and WRITE_MEM reach the same point). If phase B gives
  `failed` but MREAD sees the stub, there is a real DMA/fetch divergence - investigate
  MMIO attributes, not icache.
