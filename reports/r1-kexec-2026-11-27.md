## Instrumentation audit (OFFLINE_ONLY)

Five files in `.src/linux-amlogic` carry 96 added lines:

| File | Addition |
| --- | --- |
| `arch/arm64/include/asm/processor.h` | `r1_mark_phys` prototype in `compat_start_thread`; logs entry PC and T bit |
| `arch/arm64/mm/fault.c` | `R1_EVID_PHYS 0x075fb100`, `r1_mark_phys()`, and a hook in `do_mem_abort()` for EC 0x20 / FSC 0x10 |
| `fs/binfmt_elf.c` | marker after `elf_check_arch()` in `load_elf_binary()` |
| `fs/exec.c` | in `exec_mmap()`: read `ttbr0_el1`, `tlbi vmalle1; ic iallu; dsb sy; isb` |
| `kernel/panic.c` | `pstore_io_save()` stub exported GPL, logging five args at `0x075fb140` |

Findings:

- `r1_mark_phys` is normal `.text` (`T ffffff8009099808` in the instrumented
  `System.map`), not `__init`, and does not sleep. Slots `0x075fb100..0x150`
  are inside ramoops `[0x07400000, 0x07600000)` and do not overwrite the
  round sentinel at `0x075fb000`. Store + `dsb` + `civac` is correct for
  survival across reset.
- `0x82000010` decodes as EC `0x20` (IABT from EL0) with FSC `0x10` (external
  abort, EA/S1PTW clear), so the fire 11 fault would enter the hook. Slots: 0
  magic, 1 ESR, 2 FAR low, 3 PC, 4 TTBR0 low, 5/6 PTE low/high, 7/8 MAIR,
  9 PGD low, 10 PMD low, 11 `exec_mmap` flush marker. `show_pte()` prints to
  printk. Gaps: no `page_table_lock`, no THP/devmap guard, 32-bit truncation.
- The `exec_mmap` flush is architecturally valid but is a weak hypothesis:
  the ESR points at a wrong PTE target/attributes, not stale icache, and the
  fault happens late in `.text` after a long run.
- The `pstore_io_save` stub exists because the symbol is missing from the
  tree; `mali.ko` and `vpu.ko` import it. Its CRC is `0xa5e91f52` vs stock
  `0x95f5aeea`. In this tree `check_version()` only warns, but real calls
  would stop in the stub and not persist a pstore record.

## Secmon reservation hypothesis (OFFLINE_ONLY, FORCE MEDIUM)

`artifacts/aquaman.dtb` declares `reserve_mem_size = 0x300000`, secmon CMA
`size = 0x400000` and `alloc-ranges` size `0x400000`. The live FDT
`artifacts/aquaman-linux-fdt.dtb` (61,440 B, sha `9f45ccb9...`) declares
`0x2300000`, `0x2400000`, `0x2400000`. The `a4ff2fb7...` dump named in the
fifth round is no longer in the repo; its values cannot be re-verified, but
the current live FDT has the large values.

Mechanism supported by source: `drivers/amlogic/secmon/secmon.c:73-86` reads
`reserve_mem_size` and calls `dma_alloc_from_contiguous()` after
`of_reserved_mem_device_init()`. With the small DTB the driver takes 3 MiB of
a 4 MiB pool, leaving `0x5300000..0x5400000` as reusable CMA; PFN `0x5307`
falls in that hole. With the large DTB the driver takes 35 MiB and covers it.
`reports/round19-candidates/02-c2.md` shows `0x05300000` is unreadable from
non-secure context.

What is NOT supported: no evidence links user VA `0x49104` to PFN `0x5307`.
Only the `patch_dtb.sh` comment asserts it. A page-cache fill from an
inaccessible page would more likely fault as a data abort first. The
compat page-table hypothesis remains equally compatible with the ESR. The
PTE captured by the new instrumentation is the missing fact.

No overlap: the enlarged region `[0x5000000, 0x7400000)` does not cover the
Image (`0x2ac80000`), the CMA pool (`0x2ac00000`), the staged initrd
(`0x2c87e000`), ramoops (`0x7400000..0x7600000`) or the crumbs.

Candidates: use `aquaman-r1-secmon-fix.dtb` (`56e286c3...`) when firing with a
initrd wrapper; use `aquaman-r1-live-secmon.dtb` (`3f50b0cd...`) for a no-initrd
fire. The former has `loglevel=8 ignore_loglevel`, `console_size=0x20000`,
`dm=`/`root=/dev/dm-0`, `r1probe=DEADBEEF` and initrd placeholders; the module
rewrites the initrd properties in both cases.

## Compat32 and pivot_root (OFFLINE_ONLY)

- `initrd-compat32.cpio.gz` (`c15eeb16...`, 456 B) contains an ELF32 ARM
  `init` (33,240 B, entry `0x8000`, one RWE PT_LOAD) with `write=4`,
  `reboot=88`, `exit=1` and marker `R1_COMPAT32_EL0_A7C3F19D`. It is the only
  prepared payload that separates compat page tables from mount/chroot. The
  current `compat32.S` builds a different binary (`R1_EVIDENCE_5A31C0DE`);
  do not confuse the two. `/dev/console` writes do not reach printk, so the
  marker string is not expected in pstore; the exit code is the oracle.
- `pivot-root.S` uses the switch_root idiom: `mkdirat("/root")`, 4 s
  nanosleep, `mknodat` for `mmcblk0p18`, `mount("/dev/block/dm-0")` with
  fallback to `mmcblk0p18`, `chdir("/root")`, `pivot_root(".", ".")`,
  `umount2(".", MNT_DETACH)`, `chdir("/")`, `execve("/init")`. Failures exit
  with `10+errno`, `20+errno`, `30+errno`, `70+errno`, `80+errno`,
  `90+errno`, `100+errno`, `110+errno`.
- In the initrd path there is no device-mapper target: `dm-0` does not exist
  and the fallback to `mmcblk0p18` is always the effective path, as fire 11
  confirmed (`EXT4-fs (mmcblk0p18): mounted filesystem without journal`).
- The `FileDescriptorWhitelist` / `/proc/self/fd/N` rationale in the source
  comment is speculative: `/proc` was never mounted inside the manual root,
  the whitelist runs in system_server much later, and the init died ~15 ms
  after the mount. Pivot_root is a second mount path, not a fix for the
  observed IABT. Priority: low.
- Candidate is `initrd-pivot2.cpio.gz` (`630027e8...`); `initrd-pivot.cpio.gz`
  (`efe959b6...`) is an older variant with extra strings and is discarded.

## Cross-route control over USB DL (OFFLINE_ONLY, NOT RUN)

`tools/aq_usbdl.py` already boots a plaintext modified Image to
`sys.boot_completed`, zygote and root (round 3 of
`reports/usbdl-port-aquaman-2026-11-26.md`). It is therefore a valid control
for the same Image that fails under R1.

- For a plaintext Image the correct gate patch is `entry`:
  `00 00 80 52 c0 03 5f d6` at `0x37e19ea8`. The `cbz` patch is only for the
  encrypted stock `boot.img`.
- Sequence: `adb pull` the clean Image, `python3 tools/aq_usbdl.py mkimg`,
  enter optimus (`adb reboot fastboot`, `fastboot oem update 5000`),
  `identify`, `importbootargs` with the full cmdline plus a unique marker such
  as `aqusbdl=r1attr`, then `--yes --boot boot <img>` (write at `0x1080000`,
  patch, flush, `bootm` via `0x30`).
- `r1probe=DEADBEEF` will NOT appear on this route: cmdline comes from
  `importbootargs`, not from the R1 DTB. Oracles are the dmesg banner, the
  marker, `sys.boot_completed`, zygote and `/dev/root ext4 ro`.
- Decision: boots with the same Image -> fault in the R1 handoff (inherited
  memory/GIC/DMA state, TTBR0/MAIR/SCTLR, load address); same SIGBUS at
  `0x49104` -> fault in the kernel build/config and R1 is exonerated; no data
  -> inconclusive, do not repeat.
- I have not run entering optimus, `importbootargs`, the ~27 MB RAM write, the
  BL33 patch, `bootm`, or any power cycle. No efuse in the same session.

### Final analysis of the CEC blocker (OFFLINE_ONLY + live observation)

- On the stock kernel `/dev/aocec` does not exist; on `#73` it exists as
  `crw------- root root` with generic `device:s0` context. The recovered DTB
  and the live FDT differ only in `/chosen`, `/memreserve`, the `memory@0` reg
  and two dummy battery/charger statuses - no CEC-related node difference.
  `CONFIG_AMLOGIC_CEC` and `CONFIG_AMLOGIC_AO_CEC` are enabled in both configs.
- Vendor modules built for the stock kernel fail to load on `#73` with CRC
  disagreements (`amvdec_*`, `vpu`, `mali`, `optee_armtz` panic path). The
  source tree is the close-family `3d4ab79e` approximation, not the exact
  Xiaomi tree, so this ABI gap is not fixable by a config tweak.
- Result: the custom kernel reaches userspace and framework via R1, but full
  Android (`sys.boot_completed=1`, zygote plus window under `#73`) is blocked
  by the CEC HAL dependency, reproduced identically over USB DL.
