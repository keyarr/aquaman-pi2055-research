# kernel-smoke-test — M1: EXECUTED, FAILED (payload never executes)

> **The root cause hypothesis in this file is incorrect.** The original text stated
> "bootm never reads the download bytes on this build". The real cause is different:
> the download *is* read, and is located where bootm reads, but **BL31 rejects
> any image lacking an AMLSECU signature** prior to any format validation.
> Origin: `aml_sec_boot_check` (SMC) in `common/cmd_bootm.c:142`,
> and the device is secure-fused.
>
> The distinction matters because it changes what to test next: if it were an address
> problem, the next step would be hunting the right address. It is not. The next
> step would require a valid AMLSECU signature, or a command that bypasses the
> SMC — and `booti`/`go` are not compiled into this build (E8).
>
> Current reading: `reports/fastboot-memory-flow.md` §6,
> `reports/custom-kernel-execution.md`. The protocol and artifacts below
> remain valid as a record of what was attempted.

status: M1a, CTRL, M1b, M2, and E1 run (see `fastboot-boot-verdict.md`).
15× delay without shift in return time; real 26 MB kernel returning in
19 s. Conclusion: **none of our bytes executed** — the root cause is the SMC gate,
not the read address.

## why M1 exists

Reboot-to-Android after a raw payload is the REJECTION outcome (`Wrong Image
Format` → `do_reset`), not proof of execution (see `fastboot-kernel-path.md`
§3). M1 replaces "instant reset" with "delay + reset": if reboot delays, the
payload executed. If it returns immediately, it was rejected (or §2 from the other report
bit: `load_addr` vs download addr).

## artifact

`m1_boot.img` (4096 bytes, generated by `tools/mk_m1_boot.py` from
`tools/m1_delay_stub.S`, Linaro 6.3.1):

- header `ANDROID!` v0, `kernel_addr 0x1080000`, `page 2048`, no ramdisk/second;
- 112-byte kernel = valid ARM64 Linux header (`b +0x40`, magic `0x644d5241`
  @0x38, `objdump` verified) + nested loop 4000×1M (~seconds-scale, two orders of
  magnitude above reject) + `HVC PSCI SYSTEM_RESET` with the same fid as the original
  stub (`0x84000009`) + fallback `wfi`.

## protocol (1 reboot, RAM-only, non-persistent)

```sh
adb reboot bootloader            # single reboot of session
fastboot oem printenv loadaddr   # read-only; resolves §2 (actual load_addr)
time fastboot boot m1_boot.img   # measure time until USB re-enumeration
adb wait-for-device
adb shell getprop ro.boot.bootreason  # compare with stock baseline
```

## outcome interpretation

| observed | verdict |
|---|---|
| reboot in ~1-2 s (matches raw stub) | rejected OR bootm read another address (§2). Check `loadaddr` and repeat |
| reboot in ~10-60 s | **M1 PASS**: Linux-Image-path executed into payload |
| does not return (hangs) | executed and HVC failed to reset (unexpected EL?) → physical power cycle, revise stub to SMC Fid 32-bit or `wfi`-only + timeout |

## baseline for comparison

Prior to M1, record 1 stock boot: timing `reboot`→`device` and
`ro.boot.bootreason`. Without this, "delay" has no baseline reference.

## what M1 DOES NOT prove

That Linux boots (M2+), that the DTB works (M4), or that `load_addr` is correct in
general. Only that the bootm→payload path executes our code via `fastboot boot`.
